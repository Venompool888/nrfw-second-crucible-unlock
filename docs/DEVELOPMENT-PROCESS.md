# NRFW mod 开发流程（仓库标准）

维护者 2026-11-26 定：本仓库按 OriCoop 的工作流开发（工单先行、一单一分支、分层测试、审查后合入、PR 走公开仓库）。下面只写这个项目怎么落地，以及和 OriCoop 不同的地方。

适用对象：维护者、协作者、所有 AI 会话和小弟（pi / Codex / DSH / agy）。

## 1. 工单先行

- 所有工作都先有工单：GitHub issue（`Venompool888/nrfw-second-crucible-unlock`）加本地副本 `docs/tickets/T-xxx.md`，一张工单只管一件事。总览在 `docs/tickets/BOARD.md`，细则见 `docs/tickets/README.md`。
- 类型：**feature**（玩家用得到的功能或规则）、**task**（几小时内能完成的具体工作；大 feature 先拆成 task）、**bug**（写清在做什么、复现步骤、实际结果、期望结果、证据）。
- **维护者审批通过（去掉「待审批」标签）之前不动工。** 例外：开发中新发现的 bug 建单后可以直接修。
- 设计讨论、决定和决定的变更都写进工单的进度记录，不要只留在聊天里。

## 2. 分支和提交

- `main` 上不能有坏代码。每张工单一个分支 `t/T-xxx-slug`，从最新的 `main` 拉出。
- 每个分支用自己的 worktree：`git worktree add ..\crucible-mod-wt\T-xxx -b t/T-xxx-slug main`。**不在主目录切分支。** worktree 里没有被忽略的 `vendor/` 和 `.dotnet/`，用目录联接指回主目录。
- 提交小而完整，信息以工单号开头：`T-001: …`。提交身份用 GitHub noreply 邮箱，AI 参与的提交带 `Co-Authored-By`。
- 经常把 `main` 合进自己的分支，合完重跑测试。

## 3. 测试分层（本项目的「CI」）

本项目**不能自动启动游戏**（项目约束），所以没有 OriCoop 那样的实机自动测试层，由维护者试玩加插件日志代替。

| 层 | 什么时候跑 | 跑什么 |
|---|---|---|
| 1 | 每次改动 | 对应插件的构建 + 纯逻辑测试 + PE 元数据审计（如 `tools/NecromancyHookAudit`），几秒，不开游戏 |
| 2 | 合入分支前 | `verify-local.ps1`；涉及试炼内容时再跑 `verify-third-trial.ps1`（需要本地离线资源） |
| 3 | 维护者试玩 | 只能由维护者本人启动游戏。插件把关键步骤写进日志，试玩后由会话读日志核对，结果记进工单 |

- 挂 hook 的方法签名必须由第 1 层的元数据审计逐个核对，不能只靠编译通过。
- bug 修复要带回归测试：能写成纯逻辑测试的就写（修复前失败、修复后通过）；只能实机观察的，在工单里写明日志判据（看哪一行、什么值算修好）。
- 新测试要能失败：用几组错误输入证明判定会挂。不准用改弱或删除断言、跳过测试、对特定输入特判的办法让测试变绿。

## 4. 安装测试版

沿用项目现行授权：自研 mod 完成第 1、2 层后，确认游戏已退出就直接安装测试版；先备份插件、配置、运行日志，涉及存档状态的再备份相关角色档；留回滚脚本，不算哈希。游戏运行时不替换插件，也不结束游戏进程。

## 5. 合入 main（相当于 PR 审查）

合入前必须全部满足：

1. 已合入最新 `main`，第 1、2 层测试通过。
2. 审查过 diff，**包括测试的改动**。
3. 隐私扫描干净：分支的全部补丁和提交信息里没有真实邮箱、玩家或角色名、SteamID、本机路径、服务器地址。
4. **维护者明确同意合入**（项目约束：测试通过、试玩说「很好」都不等于合入授权）。
5. 用 `git merge --no-ff` 合入，更新工单和 `BOARD.md`。

## 5a. Push 和 PR

1. 隐私扫描通过后 `git push -u origin t/T-xxx-slug`。
2. `gh pr create`：正文写 `Closes #<issue>`、改了什么、第 1/2 层测试结果（附通过数）、风险、维护者试玩要确认的地方。
3. 合入：维护者同意后，本地 `git merge --no-ff` 合入 `main`，推送 `main`，GitHub 上 PR 随之关闭、issue 自动关闭。
4. 合入后给 issue 加「待试玩验证」，并留一条完成说明（原因、改法、测试结果、PR 链接、维护者怎么在游戏里验收）。维护者试玩确认后改「已验证」。

## 6. 日志和调试

- 插件日志带来源、时间和关键参数（实体、角色、槽位、版本），方便和试玩时间点对上；有用的日志合入时保留。
- 调试循环：先有可复现的失败（日志里的哪一行）→ 怀疑原因 → 加诊断或测试验证 → 定位 → 修 → 回归。不靠猜着改。
- 日志分析按项目约定委派，主会话核对关键证据后再下结论。

## 7. 试玩

- 试玩前定具体目标（例如「召一个随从，传送后血量不回满」）。
- 原始素材（日志、截图、录音）只留本机，不进仓库。问题对应到工单，严重程度按影响 × 频率。
- 修好的工单在下一次试玩确认后才标「已验证」。

## 8. 公开内容

- issue、PR、提交信息和仓库文件都是公开的：不写真名、角色名、SteamID、本机路径、存档文件名。需要指代角色时写「测试角色 A / B」。
- 本地研究文档（仓库外的 `doc/`、`backups/`）可以保留完整信息，但不复制进仓库。
