# Simulation content initialization order — static review, 2026-10-10

Scope: read only inspection of the existing game IL2CPP metadata, GameAssembly PE bytes, generated interop PE, mod source, and the separately delegated launch-log review. No game or game DLL was executed by this review. Evidence files: `init-metadata/selected-declarations.md`, `init-disassembly.txt`, `content-init-interop.txt`, and `log-review.md` in this directory.

## Failure and exact ordering

The observed launch reached `[third-trial] SIMULATION READY` and then failed inside `Quantum.InitializeContentSystem.ExportRandomAssets` with duplicate storage key `370725232116713263`. That key is the shared `team_guid` in `research/enemy-restoration/bindings.json`. The stack in `log-review.md` places `ExportRandomAssets → Initialize → OnInit → QuantumGame.InitSystems`. This ties the collision to the early mod storage registration followed by official random-asset export; the log alone did not identify ownership, but the catalog key and both registration paths resolve it.

Native `QuantumGame.InitSystems` (#41245, VA `0x185bf68e0`) iterates its system arrays and invokes virtual system initialization (#41245 disassembly `0x185bf6a00..0x185bf6a57`, `0x185bf6b00..0x185bf6b98`). `InitializeContentSystem.OnInit(Frame)` (#44271, VA `0x18597aa20`) calls `Initialize(Frame)` at `0x18597aa37`. The latter calls `ExportRandomAssets(Frame)` (#44275) at `0x18597b466`, then continues other initialization, including `ExportActivities(Frame, WorldLUT)` (#44274) at `0x18597c2c5`; it returns at `0x18597c8b6`. Thus an `OnInit` postfix is later than *all* of this official content initialization. An `ExportRandomAssets` postfix would be too early for later caches.

The generated interop PE declares `Il2CppQuantum.InitializeContentSystem.OnInit(Il2CppQuantum.Frame f): void` as public virtual and uses the normal `il2cpp_runtime_invoke` bridge; see `content-init-interop.txt`. Harmony can target `typeof(InitializeContentSystem), "OnInit", new[] { typeof(Frame) }` with `Frame __0`, exactly parallel to the old `StartOfFrameSystem.OnInit(Frame)` target. The latest source already changes both `EnemyRestorationRuntime` and `ThirdTrialRuntime` registrations to this target; the two registrations must move together because either early call can insert the shared TeamData storage key.

## Why the later hook still has the necessary dependencies

The failed launch's `SIMULATION READY` line was emitted after registering the restored assets, ten trees, attachment blocks, storage records, and private playlist from the *earlier* StartOfFrame callback. Consequently the Frame, resource manager, asset serializer, dynamic asset database, and `InstanceDataStorage` were already callable before `InitializeContentSystem.OnInit`; they remain available at its postfix within the same `QuantumGame.InitSystems` pass. This is an observed capability of that run, not an assumption based on class names. The original donor assets and shared enemy TeamData are static QDB resources, and the later hook only reads/clones them; it does not depend on their having been placed into any random spawn pool.

The private NPC has `SpawnRate=0`, so official `ExportRandomAssets` need not discover it. The normal third-trial spawning path is a direct `AssetRefNpcData` replacement in `DynamicNpcSpawnerData.Spawn`, not an official random-pool selection. Static disassembly of that Spawn path (see `research/third-trial/dynamic-spawn-plan-review.md`) shows it resolves the supplied NPC asset, then `RuntimeNpcAttachmentsId` from its GUID and `NpcDataId` from the supplied parameter. The mod explicitly populates those two storage entries after content initialization. Static donor weapon, view, team, and related references are read from the resource manager and copied/ref-linked; the late registration does not require a new official NPC alias to appear in a global random pool. Unity view readiness remains a separate gate, and the streaming/spawner scope checks operate when those later systems run, after system initialization. This is a static ordering argument; it is not evidence of successful gameplay.

## Important exception-path caveat

Native `InitializeContentSystem.OnInit` catches an exception from `Initialize`, logs through Frame diagnostics, and reaches its return (`0x18597aa42..0x18597ab55`). A Harmony postfix can therefore run even when official content initialization failed. The postfix must not interpret callback arrival as proof of official export success. Before publishing `SIMULATION READY`, verify an official completed-content sentinel through `InstanceDataStorage` (at minimum the static enemy `TeamData` key points to the expected resource; preferably an item exported after TeamData or a native content-completion marker), and fail closed if absent. A `ResourceManager.GetAsset(TeamGuid)` check alone is insufficient: the static resource may exist before its storage export. Existing mod storage `Ensure` checks detect pointer conflicts and must remain. Do not suppress or overwrite an official initialization exception.

## Recommended production change and limits

Keep the restoration and third-trial postfix logic, per-Frame readbacks, source/entry/spawner whitelist, and view readiness gates unchanged; move both simulation postfix hooks to `InitializeContentSystem.OnInit(Frame)` and gate them on completed official content. This defers 43 private dynamic assets, private tree/attachment storage, and playlist until official content export finishes, eliminating this specific early TeamData collision. If a future original export enumerates the dynamic DB rather than only static content, the new sequence also avoids exporting private assets into native random pools. The source's `SpawnRate=0` and direct Spawn argument remain essential.

This review cannot prove that all future systems accept late dynamic registration, that every static resource alias survives a Unity resolver reset, or that game entry/spawning works. A new user-driven launch must establish `InitializeContentSystem.OnInit` finished without the duplicate key, official activity pools exist, both modules report readiness, Unity views report readiness, and the scoped third-trial spawns/clear sequence work. No launch was performed here.
